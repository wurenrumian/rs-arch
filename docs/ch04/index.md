## 一句话

一条 lane 的一生只做三件事：把请求写进对端预注册好的槽位、让对端看见「就绪」、把结果写回本端槽位。

整个过程不经过内核，也不经过任何 RPC 框架，是 RecStore 自己搭的一套协议。
真正需要「网络软件」配合的地方只有一处：两端在建连之前互相交换连接元数据，也就是下文的控制面。
它跑在 0 号分片上的一个 gRPC 服务里，默认地址 `127.0.0.1:25100`，只交换连接元数据、就绪与健康状态，从不进入读写热路径。

## 本章覆盖什么

覆盖：槽位协议与全局地址、连接与内存注册、客户端批量栈、服务端扫描与响应、控制面与部署契约、两种响应模式的真实差异。

不在本章：其它三种传输与客户端工厂（第 03 章）、存储引擎（第 05 章）、Python 计算层与基准工具（见本章末尾的「与相邻章节的接口」）。

## 它们怎么串起来

先看控制面（第 6 块）：两端各自发布自己的连接元数据，客户端等到目标分片报「就绪」之后，才建立自己的槽位视图。

数据面按槽位协议工作（第 1 块）：客户端把描述符与载荷写进对端的请求槽位，最后单独写一个提交字表示就绪；
服务端轮询到这个字，取出请求。读请求由响应模式（第 5 块）决定是直接搬真实行，还是先拷进本地缓冲区；
写请求按载荷类型落到更新或建表（第 4 块）。结果连同状态字写回客户端槽位（第 3 块）。

任何一步出错都进错误分层（第 7 块）：谁能检测、要不要置脏、能不能靠重建治好，都在那里判定。
重建本身是双边握手，靠世代号把旧连接的迟到完成挡掉（第 8 块）。

## 核心概念表

完整名单（含每个概念对应的代码符号）见[术语表](/guide/glossary)。

| 概念 | 一句话 |
| --- | --- |
| lane | 一条独立的 RC 连接，连同它独占的设备、队列与内存注册 |
| 槽位 | lane 上一块按固定偏移切好的注册内存，请求与响应各占一半 |
| 描述符 | 请求开头那 192 字节，写明这次要读什么、写什么 |
| 提交字 | 客户端最后单独写的一个 64 字节控制字，表示「请求已就绪」 |
| 状态字 | 服务端最后单独写的一个 64 字节控制字，表示「结果已就绪」 |
| 世代 | 一次重建的编号，用来挡住旧连接的迟到完成 |
| 脏 | lane 暂时不可用，等待者立刻失败而不是阻塞 |
| 回退 | 行无法直接寻址时，整批改走拷贝路径 |

## 建议读法

- 只关心一次读怎么完成：第 1 块 → 第 2 块 → 第 3 块 → 第 5 块。
- 关心自愈与故障：第 7 块 → 第 8 块，顺序不要颠倒。先失序会让「谁标记脏、谁去重建」失去上下文。
- 只想知道怎么配置和部署：第 6 块的 flag 表，加上第 9 块的不变量表。
