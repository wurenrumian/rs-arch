# 这个站怎么读

这是一份**架构讲解**，不是 API 文档。它回答的是“为什么这样设计、这样设计会在哪里出问题”，
而不是“这个函数有几个参数”。所以每一章都不按目录顺序排，而按**问题**切成若干块：
一块只讲一件事，讲完就停。

六章共 47 块。每章的开头是一张**阅读地图**（一句话、部件表、关系、概念表、建议读法），
之后每块一页，页面底部有“上一块 / 下一块”可以顺着读。

## 每块为什么长这个样

一块固定回答五件事，顺序不变：

| 小节 | 它回答什么 |
|---|---|
| 它是什么 | 这个部件在读者已掌握的概念上怎么定义，不引入未解释的生词 |
| 它为什么存在 | 缺了它会卡在哪一步、产生什么异常 |
| 它和谁接 | 上游输入、下游交付，或者生效的具体时机 |
| 代码位置 | 落到 `相对路径#符号`，方便直接跳去看 |
| 交付一句 | 这一块闭合了什么问题，下一块接的是什么 |

这种写法牺牲了一点“完整性”：同一个类型可能在两章各出现一次，各自的语境不同。
拿它当手册查的时候，用侧栏或搜索；顺着读的时候，按“上一块 / 下一块”走。

## 证据标签

正文里的事实分三档，混在一起会误导人，所以显式标注：

- **源码事实**：能在仓库里直接看到的代码、常量、分支。
- **推断**：由代码结构推出来的行为，没有运行时验证。
- **待验证**：需要构建、硬件或实测才能确认的结论，统一收在
  [未确认清单](/quality/unknowns)。

代码引用统一写作 `相对路径#符号`（类名、函数名、宏、字段），不引用行号——行号会随提交漂移。

## 三条阅读路线

**新人 1 天**：第 01 章的[仓库地图](/ch01/repo-map)与[三层调用链](/ch01/call-chain) →
第 02 章的[读路径](/ch02/read-path) → 第 03 章的[客户端栈与选型](/ch03/client-stack) →
第 05 章的[组合矩阵](/ch05/composite-matrix)。

**改传输或性能**：第 03 章的[协议与命令](/ch03/protocol)与[分片与路由](/ch03/sharding) →
第 04 章全文 → 第 06 章的[改动 → 验证路径](/ch06/verification)。

**改存储**：第 05 章的[读路径](/ch05/read-path)与[写路径](/ch05/write-path) →
[分层策略](/ch05/tiering) → 第 06 章的[测试地图](/ch06/test-map)与[基准地图](/ch06/benchmark-map)。

只想先建立整体印象，读[十条核心事实](/guide/facts)就够了。

## 与代码仓库的关系

本站是**只读**的：不构建 RecStore，不拉取 `third_party` 子模块，也不提供可运行示例。
正文里的结论来自对源码的阅读，凡是需要跑起来才能确认的，都写进了“未确认清单”，不会假装有结论。

版本基线是上游 `1f340167d`。代码继续变动之后，请按每章末尾的**证据索引**复核，
并优先跑第 06 章的验证表。
